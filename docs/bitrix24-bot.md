# Битрикс24: как создать чат-бота (проверено на portal.seafishport.ru)

Коробка (`is_cloud=0`), REST-ревизия **35**, пользователь **81** (админ, `is_integrator=0`).
Всё ниже получено живыми запросами 2026-10-28, а не из документации.

## 0. Транспорт, который реально работает

Входящий вебхук = `https://portal.seafishport.ru/rest/<USER_ID>/<SECRET>/`, вызов — `POST`
на `<webhook><method>.json` с обычными form-параметрами. Никакой авторизации, куки не нужны,
из чистого `requests` работает. Проверено: `imbot.v2.Revision.get` → `{"rest":35,...}`.

Портал — **не** самоподписанный, `verify=True` проходит.

## 1. Где это лежит в UI

- «Разработчикам» → вкладка **«Интеграции»** (`/devops/list/`) — таблица всех вебхуков
  (`ID / Пользователь / Название / Доступы / События / Виджеты`).
  Панель и карточки открываются в **same-origin iframe** `...?IFRAME=Y&IFRAME_TYPE=SIDE_SLIDER`
  (важно для автоматизации: в DOM верхнего документа контента нет).
- Карточка интеграции: `/devops/edit/in-hook/<ID>/` — обычные входящие вебхуки,
  `/devops/edit/bot-notify-staff/<ID>/` — приложение-бот (создаётся мастером
  «Информировать сотрудников в чате»).
- На карточке бота есть: поле «Вебхук для вызова rest api» + кнопка «ПЕРЕГЕНЕРИРОВАТЬ»,
  блок «Создание бота» (Название*, **URL обработчика***, Тип бота*) и «Генератор запросов».

На портале уже есть вебхук **ID 15 «Информировать сотрудников в чате»**, тип `bot-notify-staff`,
доступ «Создание и управление Чат-ботами» (= scope `imbot`), созданный нами же ранее.
Его вебхук-URL годится для вызовов прямо сейчас.

## 2. Модель скоупов (важно, отличается от ожиданий)

Скоуп у вебхука **один набор на весь токен**. У ID 15 это только `imbot`, поэтому:

| вызов | результат |
|---|---|
| `imbot.v2.Revision.get` | ок |
| `imbot.v2.Bot.list` (с `botToken`) | ок, `{"bots":[],...}` — ботов пока нет |
| `im.message.add` | `insufficient_scope` |
| `user.current` / `user.get` | `insufficient_scope` |

Значит для задачи нужно **два скоупа в одном токене**: `imbot` + `im` («Служба сообщений» /
«Чат и уведомления») + `user` («Пользователи (базовый)» — для MAP GLPI-исполнитель → USER_ID).
Варианта: расширить доступы у ID 15 или завести свой вебхук под GLPI (чище: свой, чтобы
не смешивать с чужой интеграцией).

## 3. Мифы из ТЗ, которые проверка не подтвердила

1. **«botToken нужен только при авторизации через вебхук; для OAuth не нужен»** — неверно для
   этой коробки: **все** `imbot.v2.*` через входящий вебхук требуют параметр `botToken`.
   Без него: `BOT_TOKEN_NOT_SPECIFIED`. С ним `Bot.list` отработал.
2. **«botToken нужен только своей токен»** — да, токен мы задаём сами при регистрации,
   и он же используется как параметр доступа.
3. **«`imbot.v2.Chat.list` / `imbot.v2.Chat.create` доступны»** — **нет**. Контроллер
   `Bitrix\Imbot\V2\Controller\Chat` существует, а экшенов нет:
   `Could not find description of list/create in Bitrix\Imbot\V2\Controller\Chat`.
   `imchat.add` → `ERROR_METHOD_NOT_FOUND`. То есть **создать чат и получить dialogId
   через imbot.v2 здесь нельзя** — см. п. 5.
4. Проверка «401 vs 404» на `/rest/<method>.json` без авторизации определяет **существование
   контроллера**, а не экшена. Выводы «метод есть» по 401 делать нельзя — только по реальному вызову.

## 4. Контракт регистрации бота (снят победными вызовами, ничего не создано)

```
POST <webhook>imbot.v2.Bot.register.json
  botToken=<придуманный секрет>          # обязателен, иначе BOT_TOKEN_NOT_SPECIFIED
  fields[code]=glpi_notify              # fields обязан быть МАССИВОМ (fields[...]=),
  fields[name]=...                      #   иначе "Invalid value {code} ... type array"
  fields[type]=bot
  fields[eventMode]=fetch
  fields[properties][name]=GLPI Заявки
  fields[properties][workPosition]=Поддержка
```

Ошибки по шагам: без `botToken` → `BOT_TOKEN_NOT_SPECIFIED`; без `fields[code]` →
`BOT_CODE_REQUIRED`; `fields` не-массивом → ошибка типа параметра.
`imbot.v2.Bot.get` требует `botId` или `code`. Метод идемпотентен по `code` (по заявлению
вендора — **не проверено**, проверять в момент регистрации).

`eventMode=fetch` ⇒ обработчик с публичным URL не нужен; в UI-мастере он требует URL —
это ограничение мастера, REST его не требует.

Отправка (цель, ещё не проверена — нет `im`-скоупа и dialogId):

```
POST <webhook>imbot.v2.Chat.Message.send.json
  botToken=...  botId=<int>  dialogId=chat<chatId>
  fields[message]=...   fields[urlPreview]=false
```

## 5. Открытые вопросы (что мешает закрыть задачу)

1. **dialogId**. `imbot.v2.Chat.*` не даёт ни создать, ни перечислить чаты. Варианты:
   a) создать чат в мессенджере руками, добавить туда бота, взять `chatId` из URL
      (`/web/im/?chatId=<N>` или диалог `chat/<N>`) → `dialogId = "chat<N>"`;
   b) с `im`-скоупом посмотреть `im.*` (на коробке есть `im.message.add`; листать чаты —
      `im.dialog.*` требует проверки);
   c) события `eventMode=fetch` + `imbot.v2.Message.add` — если бот сам состоит в диалоге,
      `dialogId` приходит в событии (для «только слать» избыточно).
2. **@упоминания** в сообщении от бота — не проверено (`[USER=123]@Фамилия[/USER]` vs
   отдельный механизм). Проверится первым же реальным сообщением.
3. **USER_ID сотрудников** — `user.get` требует `user`-скоуп (сейчас `insufficient_scope`).
4. Реестр «GLPI-исполнитель → USER_ID»: связка по email (в GLPI есть `alternative_email`,
   в Битрикс24 — `EMAIL`), либо руками в конфиге.

экшены вызываются через `BX.ajax.runAction('<module>.controller.<x>.<action>', {data})`.

## 7. ПРАКТИКА: бот создан и пишет (2026-10-28, 02:38–02:43)

Регистрация прошла с первого вызова (вебхук ID 15, scope только `imbot` — **этого хватило для отправки**):

```
POST <webhook>imbot.v2.Bot.register.json
  botToken=<наш секрет>
  fields[code]=glpi_notify  fields[secret]=<тот же секрет>
  fields[type]=bot  fields[eventMode]=fetch
  fields[properties][NAME]=GLPI Заявки
  fields[properties][WORKPOSITION]=Служба поддержки
  fields[properties][DESCRIPTION]=Уведомления о заявках GLPI
```

Результат: **BOT_ID = 247**, юзер-бот `id=247`, `externalAuthId=rest_bot/247`,
аватар-робик, имя «GLPI Заявки». `eventMode=fetch` — публичный URL не понадобился, как и предполагалось.
`fields` обязан быть вложенным массивом формы (`fields[properties][NAME]=...`), плоский JSON отбивается.

Отправка: `imbot.v2.Chat.Message.send` + `botToken` + `botId=247` + `dialogId` + `fields[message]`.

| диалог | результат |
|---|---|
| `81` (личный диалог с пользователем) | ✅ id 420612 — работает **без** предварительного добавления |
| `chat7018` до добавления бота в чат | ❌ `ACCESS_DENIED` |
| `chat7018` после добавления | ✅ id 420614 |

**`ACCESS_DENIED` = бот не участник чата.** API-способа добавить бота в чат на этой коробке нет:
у `Bitrix\Imbot\V2\Controller\Chat` существуют только `Message.send/update/delete`, `get`, `leave`
(`join/invite/addUsers/createChat/list` → «Could not find description of ...»).
Добавлять нужно руками: чат → «О проекте» → «+ Добавить» → выбрать чат-бота.
Поле `countChat` в `Bot.list` при этом осталось `0` — не ориентироваться на него.

`chatId=7018` — это чат «Ежедневные спринты», 9 участников. Глубокая ссылка: `/online/?chatId=7018`
(мессенджер живёт на `/online/`; `/im/` и `/web/im/` — 404).

### @упоминания — НЕ РАБОТАЮТ штатными способами (не проверено → проверено)

| вариант | исход |
|---|---|
| `[USER=81]@Курбатов[/USER]` в `fields[message]` | пришло **обычным текстом**, без подсветки (id 420615) |
| `@Курбатов` текстом | обычным текстом (id 420616) |

| `fields[attach][0][guid]=imConnector_mention` + `fields[attach][0][fields][id]=81` | `PARAM_ATTACH_ERROR: Incorrect attach params` |

Механизм `attach` существует (ошибка именно про структуру), структура не угадана.

через `im.message.add` (нужен scope `im`) и прочитать, что прилетело в `attach` у `im.message.get`.
Уведомления о сообщениях бота при этом работают (десктоп-тост приходит).
