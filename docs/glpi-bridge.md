# Мост GLPI → Bitrix24

Две функции: **(1)** новая заявка появляется в GUI, оператор смотрит карточку,
выбирает исполнителя и кнопкой «Отправить в чат» шлёт её в Bitrix24 —
исполнитель одновременно сохраняется в GLPI; **(2)** кнопкой «Актуализировать
сейчас» оператор прогоняет активные заявки своих сотрудников в чат.

**В чат не уходит ничего, пока человек не нажал кнопку.** Цикла отправки по
таймеру нет вовсе: монитор крутит только опрос новых заявок в окно. Слать
раз в день (или как удобно) — дело оператора, кнопкой.

## Файлы

| файл | зачем |
|---|---|
| `glpi_client.py` | вход в GLPI по логину, список/карточка/комментарии/актёры, запись исполнителя |
| `glpi_monitor.py` | поток с двумя циклами: новые заявки и актуализация по команде |
| `bitrix24_client.py` | отправка в чат от имени бота (`imbot.v2.Chat.Message.send`) |
| `glpi_bridge.py` | склейка: клиент GLPI + монитор + Bitrix24 + общая очередь |
| `glpi_panel.py` | окно «Заявки GLPI» (Tkinter) |
| `gui_app.py` | кнопка «Заявки GLPI» в основном окне |

Путь данных: монитор кладёт `("glpi_new_ticket", Ticket)` в
`GlpiBridge.queue`, окно забирает события своими `after(250)`.

## Ключевые грабли GLPI (11.0.7, проверено на help.basisport.ru:56780)

1. **REST недоступен** — Legacy API отключён, HLAPI требует OAuth-клиента,
   админского доступа нет. Поэтому только HTML-сессия через `requests.Session`.

2. **Источник аутентификации** — «Встроенная GLPI» (`auth=local`), а не `ldap-1`.
   Без поля `auth` GLPI тоже пускает, но источник лучше указывать явно.

3. **CSF-токен (`X-Glpi-Csrf-Token`)**:
   * AJAX (`ajax/*.php`) — токен **в заголовке**, в теле его игнорируют;
   * обычный POST (`front/ticket.form.php`) — токен **в теле** как поле
     `_glpi_csrf_token`; с одним только заголовком получаем
     `403 «Действие недоступно»`. Успешная правка отвечает **302**.

4. **IDOR-токены**. `Session::validateIDOR()` сверяет токен с тем, что
   на сервере сохранилось в `$_SESSION['glpiidortokens']`, и дополнительно
   требует, чтобы все сохранённые ключи присутствовали в запросе. В HTML
   карточки **38 разных** `_idor_token` (по одному на каждый дропдаун) —
   первый в документе брать нельзя, нужен конкретный. В `actors.php` их три
   (по числу актёров), рабочий — **последний**; с чужим токеном GLPI отвечает
   `200` и **пустым телом** (это `echo false` из `getDropdownActors`), а не ошибку.

5. **`ajax/actors.php`** (список «кого назначить») требует одновременно:
   `X-Requested-With: XMLHttpRequest`, `X-Glpi-Csrf-Token`,
   `users_right=own_ticket`, `returned_itemtypes[]=User&Group&Supplier`,
   `page=1` и **весь** `item[...]` заявки целиком (иначе `validateIDOR` не сходится).

6. **Пагинация списка** — страница 15 строк; стандартный фильтр `status=notold`
   надо отключать пустым критерием, иначе видно 58 заявок из 987.

7. **`rich_text`** — между тегами лежат переносы и табы разметки. Без
   нормализации построчно в чат уходят десятки пустых строк (см.
   `GlpiClient._rich_text`).

8. Колонка «Назначено» в списке пустая, когда исполнитель — **группа**.
   Фильтровать «назначено ли» надо по деталям заявки, не по списку.

9. GLPI рисует статусы иконками-глифами: «Решена» приходит как **«Pешена»** с
   латинской `p`. Без подмены омографов статус не опознаётся, `is_active()`
   врёт, и решённые заявки уходят в чат как активные (см. `_HOMOGLYPH`).

10. Карточку заявки (описание, комментарии, исполнитель) тянем **лениво** —
    только для выбранной. Список из 120 заявок читается за 0.7 с, а с деталями
    на каждую это были секунды.

11. В `ttk.Combobox` нельзя писать «Иванов · Первая линия» (несколько
    исполнителей одной строкой): значение не совпадёт ни с одним пунктом
    списка, и кнопка «в чат» решит, что исполнителя не выбрали. В поле —
    только ОДНО значение (главный — человек, иначе группа), а если оператор
    ничего не менял, берём текущего исполнителя автоматически.

12. Из рабочего потока нельзя звать `widget.after(...)` — периодически это
    `RuntimeError: main thread is not in main loop` (так и не загружался
    список исполнителей). Ответы из потоков уходят в общую очередь событии
    видом `("glpi_ui", callable)`, а выполняет их `GlpiWindow._drain`.

13. Подписи исполнителей могут повторяться (одинаковые ФИО) — тогда к подписи
    добавляется почта/id, иначе выбор по тексту неоднозначен.

14. **Записать исполнителя** можно ТОЛЬКО полем `_actors` — скрытым JSON
    `{"requester": [...], "assign": [...], "observer": [...]}` в
    `POST /front/ticket.form.php` (`update`, `id`, `_skip_default_actor=1`).
    Старые поля `_users_id_assign[N]`/GLPI 11 понимает наполовину: ОН ИХ
    ДОБАВЛЯЕТ, но удалить никого не может — `front/ticket.form.php` сам
    декодирует `_actors`, а `Ticket::transformActorsInput()` по разнице со
    списком в БД сам строит `_users_id_assign_deleted`. Проверять такую
    запись НО-ОП тестом бессмысленно: назначить того, кто уже стоит, —
    это ничего не доказывает; надо назначать ДРУГОГО.

15. Ответ 302/200 от `ticket.form.php` ни о чём не говорит — правка могла
    не примениться. Единственная проверка — перечитать заявку…

16. …и перечитывать её надо МИМО КЭША: `_tabs_html()` держит страницу 30 с,
    поэтому сразу после записи клиент видел СОСТОЯНИЕ ДО ПРАВКИ и рапортовал
    «назначено не применилось», хотя GLPI всё сохранил. После любой записи —
    `client.forget(id)` / `get_ticket(id, refresh=True)`.

17. Рабочий поток не имеет права бросать исключение, не сбросив `_busy`:
    кнопка «Отправить в чат» оставалась бы выключенной до перезапуска окна —
    выглядит ровно как «кнопка не работает». `_run()` ловит исключения
    сам, а неудачная отправка показывает окно с причиной.

18. `webbrowser.open()` из GUI — **запрещено**: на Windows он берёт команду
    обработчика http/s из реестра и запускает её с ожиданием (Popen().wait()),
    а браузер не завершается, пока его не закроешь. Вызов из обработчика
    кнопки — это главный поток Tkinter, окно висит насмерть. Надо
    `os.startfile(url)` (ShellExecute, возвращается сразу) — лежит в
    `web_open.open_url()`, он же кладёт ссылку в буфер, если не вышло.

19. `Listbox` с `listvariable=` при `list_var.set(...)` ПЕРЕБИРАЕТ содержимое и
    СНИМАЕТ выделение. Если выбранная заявка выводится из `curselection()`, то
    на первом же обновлении списка (а это раз в 30 с) «выбранной» остаётся
    ничего — и кнопки отвечают «сначала выбери заявку» по открытой карточке.
    Храни `self._selected_id` сам и восстанавливай `selection_set` после
    пересборки списка.

20. Новую заявку НЕЛЬЗЯ автоматически выделять в списке, если оператор уже
    держит другую: «Назначить в GLPI» сработало бы по новой заявке, а не
    по той, кому выбирали исполнителя.

21. Вложение заявки — это `<a href="/front/document.send.php?docid=N&amp;tickets_id=M">`.
    Аватарки людей ходят через ТОТ ЖЕ скрипт, но с `file=_pictures/...`, так
    что фильтр обязан требовать `tickets_id`, иначе в чат уедут фотки
    сотрудников. Скачивать файл надо своей сессией GLPI — ссылка без входа
    не работает.

22. Удаление заявки: `POST /front/ticket.form.php` с `id` + `delete`.
    Без права PURGE GLPI делает мягкое удаление (`is_deleted=1`) — проверить
    это можно только перечитав карточку, ответ 200 ничего не значит.

23. Файл в чат Битрикс24 уходит ТОЛЬКО методом `im.v2.File.upload`
    (`dialogId` + `fields.name` + `fields.content` в base64, до 100 МБ).
    Multipart-часть `files[0]` коробка принимает, отвечает id сообщения — и
    кладёт в чат ПУСТОЕ сообщение: незнакомые поля REST-слой молча
    выбрасывает. Поле `fields[files]` тоже не работает, а `fields[attach]`
    хотя бы валидируется (`PARAM_ATTACH_ERROR`). Прочитать отправленное
    обратно нечем (`imbot.v2.Chat.Message.list` на этой коробке не работает),
    так что вложения проверяют глазами.

25. Метод требует scope **`im`** («Чаты») у входящего вебхука и работает под
    его владельцем, а не под ботом: файл в чате появляется ОТ ИМЕНИ
    ПОЛЬЗОВАТЕЛЯ. Без права — `insufficient_scope`, и путать его с «файл
    битый» нельзя: текст заявки при этом уходит отлично.

26. Картинка в заявке — это НЕ обязательно вложение. Вставленное в описание
    изображение лежит в `<img src="/front/document.send.php?docid=1441
    &itemtype=Ticket&items_id=2854">`, и в исходном HTML знаки `&` и `=`
    ЗАКОДИРОВНЫ (`&amp;`, `&#61;`) — пока не раскроешь `html.unescape`,
    регулярка их не видит, и заявка «с картинкой» уезжает в чат без неё.
    Имя файла при этом знаменитое только по `Content-Disposition` при
    скачивании (`image001.jpg`), в `alt` лежит UUID.

27. Тот же `<img>` ловит и логотип из подписи письма — GLPI дедуплицирует
    документы по хэшу, поэтому один и тот же docid встречается в десятке
    заявок. Таскать его в чат не нужно, потому что выбор файлов — почковский
    чекбокс, а не одна галочка на всё.

24. `tk.BooleanVar.get()` из рабочего потока — `RuntimeError: main thread is
    not in main loop`. Всё, что читается из виджетов (галочка «вложения»),
    считается в главном потоке и передаётся в работу параметром.

## Вес вложений и фильтр по мелочи

GLPI подписывает размер у файлов из секции «Файлы» («510.36 KiB»), и парсер
несёт его в `size`/`size_bytes`. Картинки, вставленные прямо в описание,
размера не имеют: `front/document.send.php` отдаёт их потоком без
`Content-Length`, HEAD возвращает пустоту. Единственный способ — скачать,
поэтому `GlpiClient.fill_sizes` качает такую картинку ОДИН раз и кладёт тело
в сам пункт (`_blob`), а `GlpiWindow._send_attachments` берёт уже его.

Порог — `GLPI_ATTACHMENT_MIN_KB` (по умолчанию 40, `0` — не фильтровать).
Два правила, без которых фильтр врал бы оператору:

1. `size_bytes == 0` значит «размера не знаем», и мелочью не считается —
   иначе молча срезались бы файлы, которые просто не удалось померить.
2. Проверка порога продублирована в `_send_attachments`: карточка догружается
   фоном, и до замера веса галочка стоит включённой. Тронутые руками галочки
   (`_files_touched`) фоновая пересборка не трогает — решение человека выше
   автомата.

## Цикл актуализации

Кнопка «Актуализировать сейчас» (`poll_active_tickets(force=True)`) берёт
свежие активные заявки (`Ticket.is_active`: не удалена/не решена/не
закрыта), тянет детали в пуле и оставляет назначенные **нашим**. «Наши» —
`GLPI_TEAM_EMAILS` (почты через запятую) и/или `GLPI_TEAM_GROUPS` (названия
групп). Пустые настройки = «любые назначенные».

Самотёка ничего не отправляет — у монитора нет ветки отправки в основном
цикле. Чтобы не дублировать, подпись заявки (`date_mod` + число комментариев +
дата последнего) хранится в `data/glpi_state.json` и обновляется по ходу;
после ручной отправки из GUI подпись сбрасывается, чтобы чат не «отстал».

### Заявка попадает в актуализацию, если выполнены ТРИ условия

1. активна (не удалена / не решена / не закрыта);
2. категория совпадает с `GLPI_REFRESH_CATEGORY` (по умолчанию «Внутренние» —
   внешние клиенты в актуализации не нужны);
3. назначена **конкретному человеку** (или группе, которая не числится в
   `GLPI_REFRESH_QUEUE_GROUPS`). Пока в исполнителях только очередь вроде
   «Первая линия» — заявка считается неразобранной и в чат не идёт.

Плюс фильтр по команде (`GLPI_TEAM_EMAILS` / `GLPI_TEAM_GROUPS`). Категория
приходит только в строке списка GLPI, в карточке её нет — поэтому она
переносится из строки в запись заявки.

### Отправка по одной, а не свалкой

`GLPI_REFRESH_PACE` (по умолчанию 60 с) — пауза между сообщениями. Актуализация
живёт в отдельном потоке `glpi-refresh`, шлёт по заявке и рапортует в статус
`актуализация 3/10 — #2836, следующая через 60 с`; повторное нажатие кнопки
предлагает остановить (`cancel_refresh`). Проверено: при паузе 3 с реальные
интервалы вышли 3.5-3.7 с (плюс сборка сообщения).

## Упоминания в Bitrix24

Коробка `portal.seafishport.ru` (REST rev 35) рендерит `[USER=81]@Имя[/USER]`
**обычным текстом**, `attributes[mention]` принимает молча,
`attach[0][guid]=imConnector_mention` — `PARAM_ATTACH_ERROR`. Имя исполнителя
всё равно попадает в сообщение. С `USER_ID` там, однако, **две ловушки**:

1. Почтовые домены разные: в GLPI `s.onzyls@basisport.ru`, в Битрикс24 у того
   же человека `s.onzyls@seafishport.ru`. Поиск по полной почте не совпадёт
   никогда — цепляться надо за локальной частью (`s.onzyls`) или фамилией.
2. `user.get` на этой коробке **игнорирует `filter`/`CONTAINS`** и возвращает
   всех подряд. `user_by_email()` берёт первую строку — то есть возвращает
   `ID 1` на любой запрос. Правильно: читать список целиком и сравнивать
   почты/логины у себя, а не верить фильтру.

Когда добьёмся нормального упоминания — менять только
`mention_for`/`mention_text`.

## ID группового чата — с префиксом

`imbot.v2.Chat.Message.send` на эту коробку принимает `dialogId` группового
чата только в виде **`chat7018`**, а не `7018`: с голой цифрой портал отвечает
`«Указанный чат не существует»`, и логи при этом выглядят как тишина бота.
Личный диалог — наоборот, просто `81`.

Групповой чат — `chat7018`, это рабочая группа **«Ежедневные спринты»**
(`entityType=SONET_GROUP`, scrum). Бот 247 в ней состоит, поэтому отправка туда
работает; по умолчанию выбран личный диалог, а групповой включается
переключателем «куда» вручную.

Имя чата отдаёт `im.v2.Chat.get` в `result.chat.name` — на нём висит
`Bitrix24Client.chat_title()`, чтобы оператор выбирал «Ежедневные спринты»,
а не `chat7018`. Имена догружаются фоновым потоком: синхронный запрос в
момент сборки окна сделал бы паузу на весь таймаут, если портал недоступен.

Для справки: чат, который в обиходе зовут «красный чат №18», — это
`chat8506` (цвет `#df532d`), и его владелец — сам бот 247.

## Кому именно — диалог создаётся только руками

Файлы в чат грузятся от имени владельца вебхука, поэтому адресат обязан быть
участником диалога. `imbot.v2.Chat.Add` участников-людей к этой коробке НЕ
доцепляет: ни `fields[userIds][]`, ни `fields[userId]`, ни `type=SINGLE` —
`imbot.v2.Chat.Get` на созданном чате показывает `[247]`, то есть одного бота.
Вывод: бот пишет туда, где его уже добавили руками, и «отправить
исполнителю» — это не переключатель в конфиге, а отдельная доработка.

## Режимы в окне «Заявки GLPI»

Верхняя панель «РЕЖИМ»: «Заявок за раз» (GLPI слушается `glpilist_limit`, поэтому
60 заявок приходят одним запросом за ~0.3 с), «только активные», «актуализация
в чат» + интервал, «Актуализировать сейчас» (ручной прогон без счёта «уже
отправляли»), **«куда»** — переключатель адресата: личный диалог
(`BITRIX_DIALOG_ID`) и групповой чат (`BITRIX_DIALOG_ID_ALT`), причём групповой
подписывается своим именем, и подсказка, кому именно уходят заявки. По
умолчанию всегда личный диалог: групповой чат включается только ручкой в окне.

«Новыми» считаются только **активные** заявки (`GLPI_ANNOUNCE_ACTIVE_ONLY=1`):
иначе первое знакомство с историей при увеличении глубины выдавалось за поток
новых, а решённые и закрытые попадали в эфир.

Первый цикл монитора заявки **не отправляет**, а только запоминает (иначе в чат
прилетела бы история). Чтобы окно при этом не выглядело пустым, сразу после
него вызывается `show_current()` — текущие активные заявки выводятся в список
(`GLPI_ANNOUNCE_FIRST=1`, `GLPI_SHOW_LIMIT=40`).

## Запуск

```
venv\Scripts\python.exe main.py        # окно «Bot Notify Desktop» → «Заявки GLPI»
```

Нужные `.env`: `GLPI_URL`, `GLPI_USER`, `GLPI_PASSWORD`, `GLPI_VERIFY_SSL=0`,
`BITRIX_WEBHOOK`, `BITRIX_BOT_TOKEN`, `BITRIX_BOT_ID`, `BITRIX_DIALOG_ID`,
плюс `GLPI_TEAM_EMAILS`, `GLPI_TEAM_GROUPS`, `GLPI_REFRESH_INTERVAL`,
`GLPI_NEW_INTERVAL`, `GLPI_REFRESH_LIMIT`, `GLPI_AUTO_SEND`.

Бот обязан **состоять** в групповом чате — API его не добавляет, только руками.
Вебхуку обязана быть выдана группа прав `im` («Чаты») — иначе файлы в чат не
загрузятся никогда, и программа честно об этом скажет.
